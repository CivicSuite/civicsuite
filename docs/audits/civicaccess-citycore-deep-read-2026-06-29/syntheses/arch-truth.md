# Synthesis: arch-truth (2026-06-29 deep-read)

**Summary**:

The shipping CivicSuite Windows desktop is a Tauri/WebView2 shell whose business logic for all city-core workflows lives in Rust (desktop/src-tauri/src/workflows.rs, ~11K lines) — NOT in HTTP calls to the per-module FastAPI services. The Python module packages (civiccore, civicrecords-ai/app, civicclerk, civiccode, civicnotice, civicaccess) are bundled on disk inside the cpython-services payload and are consumed in only two narrow ways: (1) imported by civicsuite_runtime.services for an in-process /health bridge on http://127.0.0.1:15480, and (2) imported by civicsuite_runtime.migrate to run Alembic migrations into the local PostgreSQL during install. The supervisor spawns exactly five OS-level services (postgres, python-services, task-queue, model-runtime, file-storage) — never a separate FastAPI process per module. There is no reqwest dependency used in any Rust source, no per-module port (8050/8052/8053/8054/8066/8060) is referenced anywhere in supervisor/workflows/main, and search/answer/records/meetings/code/notice handlers all mutate a single local city-work.json state file. The repo profiles were materially WRONG on this: civicclerk's profile claims "civicclerk FastAPI server runs as a child process, desktop makes HTTP calls to /api/meetings", civiccode's profile claims "imported as `civiccode.main` by ... desktop service supervisor" and lists 11K-line workflow handlers as proof of integration, and civicrecords-ai's profile claims service spawning — none of which match the actual source. The umbrella profile is closest to correct: "no outbound module HTTP forwarding observed; modules invoked as Python library imports + task-queue async dispatch."

**Rust Vs Python Truth**:

Pattern for the 5 currently-shipping city-core modules is (C) Python libraries imported + (D) bundled for migrations only — with the EFFECTIVE business logic re-implemented in Rust (B), not delegated to Python. Per-module:

(1) civiccore — Imported by civicsuite_runtime.services for /health (services.py:20 `("civiccore", "civiccore")`) and by civicsuite_runtime.migrate for Alembic (migrate.py:56 `core_root = _package_root("civiccore") / "migrations"`, line 62 `_run_alembic("CivicCore", core_root / "alembic.ini", core_root, sync_url)`). Its `civiccore.tasks.worker` module is the ONLY module python ever spawned as a long-running OS process by the supervisor — windows-local-runtime.json:62-63 `"binary": "runtime/python/python.exe", "args": ["-m", "civiccore.tasks.worker", "--backend", "postgres"]`. No FastAPI server, just the task-queue worker.

(2) civicrecords-ai — Imported by services.py:21 `("civicrecords-ai", "app.main")` for /health. Migrations run from a runtime-side alembic tree at civicsuite_runtime/civicrecords_alembic (migrate.py:57 `records_root = runtime_root / "civicrecords_alembic"`, line 63-68 `_run_alembic("CivicRecords AI", ...)`). Bundled file: windows-runtime-payloads.json:34 `Lib/site-packages/app/main.py`. NOT spawned as an HTTP service. All "records request" logic is Rust: workflows.rs:4574 `fn create_records_request(state: &mut CityWorkState, ...)` mutates state.records_requests directly — no HTTP call to the records-ai FastAPI.

(3) civicclerk — Imported by services.py:22 `("civicclerk", "civicclerk.main")` for /health. Migrations: migrate.py:58 `clerk_root = _package_root("civicclerk") / "migrations"`, line 69 `_run_alembic("CivicClerk", ...)`. Bundled: windows-runtime-payloads.json:35 `Lib/site-packages/civicclerk/main.py`. NOT spawned as a service. The 81 HTTP routes documented in the civicclerk profile (`/meetings`, `/agenda-items`, `/motions`, etc.) are NEVER called by the desktop — workflows.rs implements `create_meeting`, `add_agenda_item`, `record_motion`, `record_vote`, `adopt_minutes`, `sign_minutes`, `archive_meeting`, `export_meeting_packet` all as native Rust functions that write to city-work.json (see workflows.rs:7677-7713).

(4) civiccode — Imported by services.py:23 `("civiccode", "civiccode.main")` for /health. Migrations: migrate.py:59 `code_root = _package_root("civiccode") / "migrations"`, line 70 `_run_alembic("CivicCode", ...)`. Bundled: windows-runtime-payloads.json:36. NOT spawned. The Phase B Section Resolution Contract (`POST /api/v1/civiccode/sections/resolve`) documented in civiccode's profile is NEVER invoked by Rust — workflows.rs:6212 `fn import_code_source`, 6696 `fn answer_code_question`, and `draft_code_guidance`/`approve_code_guidance`/`publish_code_source` are all native Rust handlers reading from city-work.json.

(5) civicnotice — Imported by services.py:24 `("civicnotice", "civicnotice.main")` for /health. NO Alembic migration run for civicnotice in migrate.py (it does deterministic/optional SQLAlchemy with its own schema, not part of the runtime migration chain). Bundled: windows-runtime-payloads.json:37. NOT spawned. The `civicnotice-calculate-deadline`, `civicnotice-complete-checklist`, `civicnotice-post-notice`, `civicnotice-export-archive-packet` Tauri actions map to PURE RUST handlers in workflows.rs (lines 2482, 2543, 2640, 4464) — workflows.rs:7691-7694 simply aliases them to the same Rust functions used by the legacy `calculate-notice-deadline`/`complete-notice-checklist`/`post-notice` paths. No HTTP call to civicnotice's port 8066, no use of its FastAPI routes.

Cross-cutting evidence that NOTHING routes to per-module HTTP services: (a) `grep reqwest|HttpClient` over desktop/src-tauri/src returns zero matches (only Cargo.lock has the transitive lib). (b) `grep 8050|8052|...|8077` over supervisor.rs returns zero matches — no module port is ever opened. (c) The only HTTP endpoint touched is http://127.0.0.1:15480/health (supervisor.rs:3663,3673), which is the in-process Python services bridge on the cpython-services payload. (d) civicaccess (the optional sixth module) ships with the SAME pattern: services.py:30 lists it in OPTIONAL_MODULE_IMPORTS, migrate.py:76-82 calls `AccessibilityReviewRepository(db_url=sync_url)` to bootstrap its schema directly (non-Alembic), and supervisor.rs:386-387 + 2045-2048 inject `CIVICACCESS_TRUSTED_WRITE_TOKEN` into the python-services process env — so when civicaccess's FastAPI routes ARE invoked (currently only via the in-process app bridge, not via Tauri), writes can be authorized. There is no `civicaccess` reference anywhere in workflows.rs (Grep confirmed: no matches).

**Frontend Module Pattern**:

main.js is a single Vite/vanilla-JS Tauri shell (~6225 lines). Module-to-UI wiring is hardcoded, not driven by the Python modules. The pattern: (1) MODULE_AREA_BY_ID at main.js:6-11 statically maps nav areas to module ids — `meetings → civicclerk, records → civicrecords-ai, code → civiccode, notice → civicnotice`. There is NO 'access' or 'civicaccess' entry, despite civicaccess being in the city-core profile. (2) Navigation chips at main.js:17-26 render the 8 areas (home, meetings, records, code, notice, search, health, settings) — NOT one per module, but per workflow area. There is no resident-facing UI surface for civicaccess yet. (3) Each workflow area has a `render<Area>Workflow()` function (e.g. renderNoticeWorkflow at main.js:3388, renderMeetingsWorkflow, renderRecordsWorkflow, renderCodeWorkflow) that emits a form panel with `<input data-work-field=\"…\">` inputs and `<button data-work-action=\"…\">` buttons. (4) Form values are written to state.workDraft by an input-event handler keyed off data-work-field. (5) Button clicks are intercepted by a click-event handler reading data-work-action, which calls handleCityWorkAction(action) at main.js:6141. That function builds a payload via workPayloadForAction(action) and invokes the single Tauri command `await invoke('city_work_action', { action, payload })` (main.js:6186). (6) The result is merged into state.app.city_work and re-rendered. (7) For browser-preview without the Tauri bridge (hasTauriBridge()===false), the code falls back to localSearchResults/localCodeQuestionResults stubs so the UI demos. The civicnotice work buttons (`data-work-action=\"civicnotice-calculate-deadline\"`, etc. at main.js:3422-3434) follow this same pattern — they invoke city_work_action and the Rust workflows.rs handler executes; the civicnotice FastAPI server is never contacted. A new module is wired in the UI by: (a) adding a render<Area>Workflow function with data-work-action buttons, (b) adding a nav entry in fallbackState.navigation + corresponding `match action` arm in workflows.rs::city_work_action, (c) optionally adding MODULE_AREA_BY_ID and module_exports_folder entries in main.rs:279-288 for export-folder routing and role-gating.
