# Synthesis: civiccore-contracts (2026-06-29 deep-read)

**Summary**:

CivicCore v1.2.0 is a Python library of shared, storage-neutral primitives (auth, audit, ingest, LLM, platform contracts, connector sync, security, search, notifications, onboarding, scheduling, release provenance, testing). It ships no HTTP server, no end-user app, and no enforcement layer — it provides ABCs, dataclasses, Pydantic schemas, SQLAlchemy ORM, decorator registries, and an Alembic migration runner that consumer modules opt into. Modules ride on civiccore by importing helpers and inheriting the shared SQLAlchemy `Base`; nothing forces them to. CivicAccess v0.4.0 pins `civiccore==1.2.0` for a release-wheel hash and for the package to be loadable by the desktop's bundled python-services health check, but in its own runtime code it touches civiccore only to read `__version__` for `/health` — it reimplements its own DB writer guard, schema-migrations table, and audit_events table instead of using `civiccore.auth`, `civiccore.migrations.runner`, or `civiccore.audit`. That gap (declared dependency vs. actual consumption) is the headline finding.

**Contracts Modules Must Satisfy**:

- Declare civiccore as a pinned dependency in pyproject.toml. Convention is the published release-wheel URL with SHA-256 (CivicAccess: `civiccore @ https://github.com/CivicSuite/civiccore/releases/download/v1.2.0/civiccore-1.2.0-py3-none-any.whl#sha256=...`). City-core modules pin v1.2.0 exactly; the desktop module_registry blocks city-core entries that don't match (see civiczone blocked at 1.1.0).
- If using LLM, prompt templates, model registry, ingestion, audit, task queue, or shared schema — inherit civiccore primitives, do NOT reimplement. Stay off the reserved placeholder packages `civiccore.catalog` (ADR-0001), `civiccore.exemptions` (ADR-0002), `civiccore.scaffold` (ADR-0003) until they ship in a versioned release.
- Migration ordering: when a module runs Alembic, its env.py must call `civiccore.migrations.runner.upgrade_to_head` BEFORE its own migrations so the baseline (`alembic_version_civiccore`) is installed first. Module migrations live under their own version_table to avoid collision. (The desktop's civicsuite_runtime.migrate enforces this order: civiccore first, then per-module.)
- ORM models that share tables with civiccore must inherit `civiccore.db.Base` so they share one DeclarativeBase metadata registry (per the v1.2.0 ingest pipeline contract on `documents`/`document_chunks`/`data_sources`).
- Module manifest (when wired into the desktop) must conform to `civiccore.platform.ModuleManifest`: module_id matches `^[a-z][a-z0-9-]{1,63}$`, declares `civiccore_min_version`, services typed via `ServiceType` literal, no `docker|wsl|linux_shell|terminal` runtime requirements for the windows_local profile, route permissions cross-reference declared permission keys, services reference declared health_check ids, no self-dependency. `validate_windows_local_manifest` raises on violation.
- Auth (when adopting shared contract): use `civiccore.auth.authorize_bearer_roles` with a `<MODULE>_AUTH_TOKEN_ROLES` env var holding JSON `{token: [roles]}`; or `civiccore.auth.staff_key_gate(env_var, header)` for the `X-Civic*-Role: staff` + `X-Civic*-Staff-Key` convention; or `civiccore.auth.authorize_trusted_header_roles` + `enforce_trusted_proxy_source` for reverse-proxy SSO with `<MODULE>_TRUSTED_PROXY_CIDRS`. Suite-session bearer requires `CIVICCORE_SUITE_SESSION_SECRET` (≥16 chars, placeholder-free) and may share revocation via `CIVICCORE_SUITE_SESSION_REVOCATION_FILE`.
- Audit (when adopting shared chain): use `AuditHashChain` for new events or `compute_persisted_audit_hash`/`verify_persisted_audit_chain` for the legacy CivicRecords-AI pipe-delimited row format. Events MUST set `source_module` for cross-module audits.
- Task handlers (when joining the shared queue): register via `@civiccore.tasks.register_task_handler(task_type)` at import time; the worker reads `CIVICCORE_TASK_HANDLER_MODULES` (comma-sep) to import them; requires `DATABASE_URL` pointing at the shared Postgres holding `civiccore_local_tasks`.
- Connector sync (when implementing a live connector): use `SyncCircuitState`/`SyncRetryPolicy`/`apply_sync_run_result` for retry+circuit semantics and `build_sync_operator_status`/`build_sync_source_status` to expose health to operators; do not reinvent the 5-failure/2-in-grace breaker.
- Search access tiers: use `access_level_allows`/`filter_records_by_access_level` with a module-owned rank map (civiclegal demonstrates the pattern) rather than hand-rolling privilege checks.
- LLM template resolution: callers register with `consumer_app=<module>` so override resolution traverses DB → in-memory OVERRIDE_REGISTRY → civiccore default in that order; the consumer FastAPI app mounts `model_registry_router` and injects its DB session.
- Backup/restore: declare `ModuleBackupHook` entries naming relative-path globs (CivicAccess: `Data/workflows/access`, `Data/exports/access`, `Data/files/access`) and assemble manifests with `build_backup_manifest` so the shared restore plan stays checksum-verified.
- Security/config: validate secrets at startup via `validate_secret_setting`/`validate_fernet_key_setting`/`validate_password_setting`/`looks_like_placeholder`; encrypt secret-bearing config at rest with `encrypt_json`/`decrypt_json`; reject blocked hosts with `validate_url_host`/`validate_odbc_connection_string`.
- Release provenance (when cutting a release): pin per-repo+per-tag workflow identity, publish `release-attestation.json` + Sigstore bundle, run `verify_release_provenance` before promoting. Org-wide wildcards are rejected.
- Reserved placeholders: ADR-0001/0002/0003 forbid any module from importing or claiming dependency on `civiccore.catalog`, `civiccore.exemptions`, or `civiccore.scaffold`; local equivalents must be ADR-documented as a temporary bridge.

**What Civicaccess Inherits**:

CivicAccess's pyproject.toml pins civiccore==1.2.0 by release-wheel URL + SHA-256 (`civicaccess @ ... civiccore-1.2.0-py3-none-any.whl#sha256=a94ce958...`). What that pin actually buys CivicAccess in its current code (v0.4.0): (1) ONE symbol — `from civiccore import __version__ as CIVICCORE_VERSION` in civicaccess/main.py:7, used to report civiccore version in `/health`. That is the ONLY runtime civiccore import in civicaccess source. (2) The verify.yml CI gate asserts `civiccore.__version__ == '1.2.0'` so a wrong pin breaks CI. (3) Module loadability under the desktop's bundled python-services (civicsuite_runtime.services calls `importlib.import_module('civicaccess.main')`, which would fail if its `from civiccore import __version__` couldn't resolve). (4) Eligibility for the city-core profile — the desktop module_registry blocks city-core entries whose `civiccore_requirement` isn't 1.2.0 (civiczone is blocked at 1.1.0 for this reason). What CivicAccess does NOT inherit despite the pin: it does NOT use `civiccore.auth` (rolls its own constant-time `hmac.compare_digest` against `CIVICACCESS_TRUSTED_WRITE_TOKEN` and the `X-CivicAccess-Write-Token` header in main.py instead of `staff_key_gate` or `authorize_bearer_roles`), does NOT use `civiccore.migrations.runner` (uses an ad-hoc `civicaccess.schema_migrations` table and `metadata.create_all` in access_review.py:111 — schema is `civicaccess-windows-local-state-v1`), does NOT use `civiccore.audit` (writes a plain `civicaccess.audit_events` table with event_id/action/subject_id/actor/created_at and NO `previous_hash`/`current_hash` linkage — there is no hash chain at all on accessibility records), does NOT use `civiccore.tasks` (no task handlers registered, the `accessibility-review`/`records-export` tasks listed in modules.json are not wired to the civiccore queue worker), does NOT use `civiccore.platform.ModuleManifest` (the manifest fields in installer/modules.json are author-time JSON, not produced from the Pydantic model — the runtime never validates against `validate_windows_local_manifest`), does NOT use `civiccore.search`, `civiccore.llm`, or `civiccore.ingest`. The pin is therefore mostly a release-line marker plus version-string source — the substantive contracts civiccore offers are available but unused. The desktop supervisor compensates for the auth gap by injecting `CIVICACCESS_TRUSTED_WRITE_TOKEN` (supervisor.rs:386-2047) and the supervisor's shared `DATABASE_URL` is opportunistically picked up by `_review_database_url` for Postgres with SQLite fallback.

**Notable Gaps**:

- Placeholder packages by design: `civiccore.catalog` (ADR-0001), `civiccore.exemptions` (ADR-0002, the 50-state public-records exemption engine), and `civiccore.scaffold` (ADR-0003, module generator CLI) are reserved namespaces with explicit no-consumption rules. README markets the exemption engine as platform scope; the package is a single docstring.
- `civiccore.ingest` ships the pipeline but no scheduler/runtime — modules must own queueing and ingestion orchestration (CivicRecords AI keeps Celery + Beat for this).
- `civiccore.onboarding` ships storage-neutral interview helpers but no web UI or persistence router.
- `civiccore.search` is normalization + RRF + access filtering helpers; no search engine, no indexer, no vector retrieval (modules pair these with pgvector queries themselves).
- `civiccore.notifications` ships deadline planning and compliance checks but no delivery queues, no SMTP/SMS adapter, no outbound orchestration.
- `civiccore.scheduling` ships cron validation + next-run math but no scheduler runtime (no equivalent of Celery Beat).
- `civiccore.verification` ships browser-evidence helpers; sovereignty verification is explicitly future work.
- No HTTP server in civiccore. The LLM `model_registry_router` is just an `APIRouter`; consumers mount it and provide the session dependency override. There is no central `/admin/models` until a host app mounts the router.
- No first-party identity provider. OIDC browser-session handling lives in module repos (CivicClerk's `oidc_auth.py` is marked as a future extraction candidate per ADR-0009 in that repo).
- No enforcement that consumers actually use civiccore primitives. ModuleManifest validation runs only when `build_module_registry` or `validate_windows_local_manifest` is called — installer/modules.json entries today are hand-authored JSON and the desktop does not appear to validate them against the Pydantic model at boot. Several modules (CivicAccess, CivicNotice, Civic311, CivicBoards) ship parallel ad-hoc `X-CivicXxx-Write-Token` HMAC guards instead of `staff_key_gate`; CivicAccess ships its own `schema_migrations` table and a plain `audit_events` table without hash chaining. CivicCore offers contracts but does not police compliance.
- Vendor write-back, credential orchestration, and vendor-specific network adapters are explicitly unshipped (README §Status). Modules that need them roll their own (CivicClerk's vendor-live-sync).
- Task queue requires PostgreSQL (`civiccore_local_tasks` uses JSONB and `SELECT ... FOR UPDATE SKIP LOCKED`); there is no SQLite fallback for the queue itself even though many modules support SQLite fallback for their own tables.
- Suite-session secret has weak placeholder rejection (`<`, `>`, `replace-`, `change-this` substrings, plus `CHANGE-ME`/`changeme`). A long but low-entropy string passes the 16-char gate; modules relying on this MUST generate from a CSPRNG.
- The LLM provider ABC explicitly omits `chat()` and structured tool-use (ADR-0004 §6 defers to v0.3.0 of the LLM surface). Modules needing multi-turn conversation must work around it.
- Migration runner intentionally commits independently of the caller's transaction (runner.py docstring): "civiccore commits independently of the caller's transaction. The baseline is idempotent, so a partial-state restart produces the same end-state." Acceptable per ADR-0003 §"Three deployment scenarios" but worth knowing — a failed module migration after civiccore commits leaves the baseline in place.
- Reserved-placeholder enforcement is by ADR + reviewer discipline, not by Python — the namespaces are importable (empty `__init__.py`) and downstream modules could shadow them without import errors.
