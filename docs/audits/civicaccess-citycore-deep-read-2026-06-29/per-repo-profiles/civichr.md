**Notable findings**:

- CivicHR v0.1.1 pins civiccore==0.3.0, which is older than city-core's civiccore==1.2.0, indicating this tier-3 module is pre-city-core and may require a dependency bump before integration.
- The installer defines default_port=8070 for civichr, but this port is never referenced in desktop runtime configs, service spawner code, or route mappers—just registry metadata.
- Civichr is intentionally deterministic and stateless by default (requires CIVICHR_WORKPAPER_DB_URL env var to persist); this aligns with CivicSuite local-first design but means it ships as a proof-of-concept draft generator, not an HRIS.
- Tests emphasize boundaries: job-description explicitly states not_a_classification_decision=True, onboarding packets do not track completion, intake templates do not track cases or recommend outcomes. This legal guardrail pattern should inform CivicAccess integration (accessibility reviews are not compliance determinations).
- The module uses SQLAlchemy's schema-aware mapping (schema='civichr' on tables, schema_translate_map for SQLite) to support both local SQLite testing and production PostgreSQL without code changes—a reusable pattern.
- Civichr offers HTTP endpoints that are read-only (GET) for retrieval and write-once (POST) for draft creation; no PATCH/PUT/DELETE—suggests workpapers are immutable records, not collaborative drafts.
