# Refutation lens: refute-revert-phase-c-is-safest (2026-06-29 deep-read)

**Claim**:

The cleanest minimal-blast-radius response right now is to revert PR #214 (Phase C), returning city-core to the proven 5-module state until CivicAccess has a working desktop integration. Per the Phase D manifest rollback_plan.

**Refuted**:

True

**Reason**:

Reverting #214 is not minimal — it is mechanically larger and riskier than leaving the registry at 6. The syntheses show Phase B/C is structurally inert: zero hits for civicaccess in main.js or workflows.rs, no spawned process, no reachable HTTP route, no UI button, no data-loss surface (the bootstrapped Postgres schema is empty because nothing writes to it). The user-visible MSI behavior is byte-for-byte identical to the 5-module build — same 8 nav tabs, same set of buttons, same workflows.rs dispatch table. So the "risk" the revert claims to mitigate (shipping CivicAccess incomplete) does not exist at runtime; what ships is dark, healthy, optional code. Meanwhile a revert touches ~25 files across two PRs and must flip in lockstep: modules.json (re-add excluded_modules NEEDS-WORK, re-demote to v0.2.0, flip selectable), verify-suite-state.py (expected_modules, source_commit_pin set, PASS line), verify-installer-plan.py (re-add to PLANNED_NON_SELECTABLE_MODULES + "six → five" string), test_module_manifest_contract.py, module_registry.rs + main.rs cargo tests (count 6→5), regenerate every install-plan.json + launcher + README under installer/generated/packages/city-core/{linux,macos,windows} via plan-installer.py, then flip "six" → "five" across STATUS.md, README.md, ANNOUNCEMENT.md, USER-MANUAL.md, FAQ.md, UnifiedSpec, compatibility matrix, release-recovery-status.md, troubleshooting.md, github-discussions-seed.md, CHANGELOG.md — many of which are already public. Then a second cleanup commit (the 0911dac analogue in reverse) to re-sync plan-installer.py launcher generation with the new lower count, or you re-introduce the exact Blocker 0911dac just fixed (launchers and install-plan disagreeing on module count). On the "fix forward in one PR" feasibility: the civicnotice precedent proves it is not just feasible, it is small. PR #193 was ONE lockstep PR that added: 4 Rust handlers in workflows.rs (which already exist as Rust no-ops/aliases for civicaccess — main.rs:262 already maps accessibility-review and records-export), renderNoticeWorkflow() with 4 data-work-action buttons, MODULE_AREA_BY_ID + navigation entry + fallbackState.modules card, static-smoke phrases, ONE cargo end-to-end test, ONE Playwright spec. For CivicAccess most of the scaffolding is already done by Phase B: token injected (supervisor.rs:386,2045), schema bootstrapped (migrate.py:76), /health reporting (services.py:30), role granted (auth.rs:539), module→folder map (main.rs:285), workflow→module requirement (main.rs:262). The remaining forward diff is smaller than civicnotice's was — add the workflows.rs arms (pure Rust over CityWorkState, exactly like civicnotice's aliases at workflows.rs:7691-7694), add the main.js panel + buttons + nav entry, optionally mount the FastAPI app on a port if the staff UI is needed (or keep it Rust-native like every other module — note that civicnotice/civicclerk/civiccode/civicrecords-ai FastAPI servers are ALL bundled-but-unspawned; Rust reimplements the business logic; civicaccess can follow the same pattern and skip uvicorn entirely). On the CI/release-recovery surface concern: those surfaces ALREADY publicly say six (PR #214 is merged as 4e0f103, the truth flip is live in README/STATUS/ANNOUNCEMENT/USER-MANUAL/release-recovery-status.md/github-discussions-seed.md). Reverting means a public "we said six, now we say five again" reversal across user-facing docs, plus contradicting STATUS.md's already-published caveat that "the six-module MSI is the next build." That is a louder signal to users than shipping the UI integration. Phase D acceptance is clean-VM, not registry alignment; the registry/truth flip Phase C delivered is a precondition Phase D needs, not something to undo. The rollback_plan in the Phase D manifest is an escape hatch for catastrophic regression, not the default — invoking it here trades a small forward integration (already 70% done) for a large backward registry sweep that re-creates a Blocker (launcher/plan drift) and a public flip-flop, with zero user-visible benefit because the current state already behaves exactly like the 5-module build.

**Risks If Kept In Place**:

- Documentation says six modules but the UI offers five — a clerk reading USER-MANUAL.md or ANNOUNCEMENT.md will look for the Accessibility tab and not find it; until the forward PR lands, support needs a one-line FAQ ('CivicAccess ships dark in 1.0.1; UI lands in 1.0.2') to avoid 'where is it' tickets
- The civicaccess Postgres schema and write-token are provisioned on every install but never used — small disk + first-run-time cost and a secret-at-rest that has no consumer (low risk: token is unreachable because no port is bound)
- MSI is slightly larger (one extra pip-installed Python package) and first-run is slightly slower (best-effort civicaccess schema bootstrap) — measurable but immaterial
- The /health JSON on 127.0.0.1:15480 now exposes a civicaccess module row with optional:true; an operator scraping it could be confused that an 'available' module has no UI surface — mitigated by the optional flag but worth a one-line note in the health-check doc
- Phase D clean-VM acceptance must explicitly assert that civicaccess being dark-but-healthy does not flip overall status to degraded (the services.py:158 logic already gates this on required modules only, but Phase D needs to verify it on a fresh VM)
- Forward-fix PR carries integration risk of its own (new Rust arms, new buttons, new tests) — but this is smaller and more reversible than the registry sweep a revert requires, and lands the actual user value
- If the forward-fix slips past Phase D's deadline, the documentation/UI mismatch persists into a GA window — schedule risk, not correctness risk; mitigated by either landing the small forward PR or by a one-commit doc patch that adds a 'not yet user-reachable in this build' callout next to every six-module mention
