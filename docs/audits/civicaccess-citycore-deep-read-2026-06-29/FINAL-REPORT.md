# FINAL REPORT — CivicSuite Module 6 (CivicAccess) integration (2026-06-29 deep-read)

_35 subagents read every repo in github.com/CivicSuite (27 repos, 2.9M tokens, 1301 tool calls, 30 minutes). Adversarial panel refuted two earlier hypotheses; this is the survived recommendation._

---

## Bottom line

Ship the forward-fix UI integration in one lockstep PR that mirrors PR #193 (civicnotice). Do NOT revert PR #214. Phase B/C already provisioned the token, schema, role grant, and folder mapping; the remaining work is small and matches the pattern every other city-core module follows.

## Plain-English summary (for Scott)

Bottom line: ship the missing UI in one focused pull request that copies what the CivicNotice integration did 5 days ago. Don't roll back the registry change.

Where things stand: the desktop app you install from the latest build (commit 4e0f103) lists six city-core modules in the docs, but the screen still only offers five workflow tabs. A clerk who reads the manual and looks for an Accessibility tab won't find one. The CivicAccess module is technically there — its code is bundled inside the installer, its database tables get created on first run, a secret write-token is provisioned, and the app reports the module as available — but there is no button anywhere in the UI that does anything with it, and no internal network address listens for it. We confirmed this directly: searching the desktop's JavaScript and Rust source for civicaccess returns zero matches in the places that would expose it to a user.

The team did this on purpose in two stages. Phase B (PR #213) wired up everything except the visible UI — the deliberate wired-but-not-yet-offered state. Phase C (PR #214) flipped the documentation to say six modules. Both stages were lockstep registry and plumbing work. The Phase C commit message itself says this is a truth/registry milestone, not the program's done-state.

The recommendation is the smallest path forward that closes the gap and is consistent with how every other module in this app already works: add the JavaScript panel and buttons, add the matching Rust handlers (mirroring exactly what CivicNotice did in PR #193), bump the version to 1.0.2, and ship. The plumbing Phase B installed is the right shape for this. Reverting Phase C is more files changed, more risk, and forces a public we-said-six-now-we-say-five-again reversal across published docs.

If the fix can't ship immediately, add a one-line callout to the manual saying CivicAccess is dark in 1.0.1 and the UI lands in 1.0.2 — that is honest and costs minutes.

### Option A: Forward-fix in ONE lockstep PR (civicnotice pattern, Rust-native)

**Description**: Mirror PR #193. Add a renderAccessWorkflow() panel in desktop/src/main.js with data-work-action buttons for accessibility-review, records-export, and any other accessibility actions the staff UI exposes; add fallbackState.modules card for civicaccess; add nav entry 'access'; add MODULE_AREA_BY_ID 'access':'civicaccess'; add CITY_CORE_PRODUCT_MODULE_IDS entry. In desktop/src-tauri/src/workflows.rs, add city_work_action match arms that mutate state.access (a new field on CityWorkState) — either thin wrappers around existing civicaccess Python helpers (PyO3 or subprocess) OR, more consistent with the existing pattern, ports of the deterministic logic from civicaccess/access_review.py, plain_language.py, multilingual.py, workflows.py into Rust. Add one cargo end-to-end test mirroring civicnotice_actions_save_notice_workpaper_and_search_result at workflows.rs:8029. Add one Playwright spec mirroring workflow-pages.spec.mjs:413-460. Bump desktop version 1.0.1 -> 1.0.2 in Cargo.toml + tauri.conf.json. Phase B scaffolding (token, schema, role, folder) needs no changes.

**Cost estimate**: Small-to-medium. The thin-Rust-alias variant (call civicaccess Python helpers via subprocess or PyO3, write results into state.access) is roughly the size of PR #193: ~5-10 Rust handler arms, ~50-100 lines in main.js, ~30 lines of cargo test, ~50 lines of Playwright. Full Rust port of access_review.py + plain_language.py + multilingual.py + workflows.py is 1-2 weeks of careful work but produces the cleanest single-architecture result and matches what civicclerk/civiccode/civicrecords-ai/civicnotice already did. Net: 2-5 days for the alias variant, 1-2 weeks for the full port.

**Upside**: Lands actual user value. Closes the docs/UI mismatch. Keeps the architecture consistent (single Rust + city-work.json pattern). No public docs reversal. Phase D acceptance becomes 'civicaccess works end-to-end on a clean VM', the natural next milestone after Phase C's truth flip. Reuses every piece of Phase B scaffolding as designed.

**Risks**:
- Integration risk of new Rust arms + buttons + tests — smaller and more reversible than a registry sweep. Mitigated by the precedent: civicnotice landed in one PR with the same shape.
- If subprocess/PyO3 is chosen for the alias variant, introduces a new in-process Python-call pattern Rust doesn't use today (workflows.rs has no PyO3). Full Rust port avoids this entirely.
- Full Rust port discards the 42-test Python suite as source of truth for the deterministic helpers — they remain in the civicaccess repo but desktop behavior is now defined by the Rust port. Mitigate with new cargo test + Playwright spec covering the desktop's actual behavior.
- Schedule risk if forward-fix slips past Phase D's clean-VM deadline — schedule issue, not correctness issue.

## Recommendation rationale

Three reasons, in order of weight.

(1) Phase B did 70% of the work needed for Option A and 0% of the work needed for Option B/C/D specifically. supervisor.rs already provisions and injects CIVICACCESS_TRUSTED_WRITE_TOKEN (supervisor.rs:386-388, 2043-2048); migrate.py already bootstraps the schema (migrate.py:72-82); auth.rs already grants civicaccess to the clerk role (auth.rs:539); main.rs already declares the workflow->module requirement at line 262 ('accessibility-review' | 'records-export' => Some((vec!['civicaccess'], false))), the exports-folder mapping at line 285, and the open-exports-folder routing at line 256; services.py already imports civicaccess for /health (services.py:29-31). The only Phase B asset Option A doesn't immediately consume is the in-memory FastAPI app object — and that's fine, because every other city-core module bundles its FastAPI server unspawned too (civicclerk's 81 routes, civiccode's 50+ routes, civicrecords-ai's 30+ routes, civicnotice's 13 routes — all bundled, none called, business logic reimplemented in Rust against city-work.json). Option A finishes the work Phase B set up for; Options B/C/D throw most of Phase B away.

(2) The civicnotice precedent is a known-good template for exactly this. PR #193 landed civicnotice as ONE lockstep PR ~58 days after the repo was created. The Rust diff was 4 alias arms in workflows.rs:7691-7694, each calling an existing Rust function. The JS diff was 4 data-work-action buttons in a renderNoticeWorkflow() panel at main.js:3422-3434. The test diff was one cargo end-to-end (workflows.rs:8029) + one Playwright spec (workflow-pages.spec.mjs:413-460). CivicAccess is in a better starting position than civicnotice was: Phase B already declared the workflow->module requirement at main.rs:262, so the Rust dispatch arms can land directly without re-declaring role gates.

(3) The alternatives cost more than they save. Option B (uvicorn sidecar + iframe) is smaller in lines but invents a new architecture pattern — every other city-core module is bundled-FastAPI + Rust-native, and adopting B means the next module will face 'should I be like civicnotice or like civicaccess?'. That cost compounds. Option C (revert PR #214) touches ~25 files in lockstep, risks re-introducing the exact launcher/plan drift Blocker 0911dac just fixed, and forces a public six->five->six docs reversal across already-published surfaces — all to mitigate a risk that doesn't exist (user-visible behavior is already identical to the 5-module build because Phase B/C are structurally inert in the UI). The Phase D manifest's rollback_plan is an emergency escape hatch, not the default.

If the forward-fix can't ship before Phase D's clean-VM deadline, Option D (one-line docs callout) is a safe interim — it costs minutes, preserves everything, and is honest. But Option A is the right destination either way.

Note on the Rust-port vs PyO3-call variant within Option A: prefer the full Rust port. The civicaccess deterministic logic (access_review.py findings, plain_language.py rewrites, multilingual.py variants, workflows.py form/publishing/ADA/tagged-PDF planners) is ~1900 lines and 42 tests; porting is 1-2 weeks but produces the cleanest single-architecture result and matches what every other city-core module already did. The PyO3 / subprocess variant is faster (days) but introduces a brand-new in-process Python-call pattern Rust doesn't use today. If schedule pressure forces the alias variant, mark each shortcut with a `ponytail:` comment naming the upgrade path to the full port.</recommendation_rationale>
